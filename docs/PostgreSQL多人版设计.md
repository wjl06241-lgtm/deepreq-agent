# PostgreSQL 多人版设计

状态（2026-09-08）：已连接用户提供的 PostgreSQL 17.9 数据库，创建 requirement_assistant 下的 9 张业务表，以及 v2 的 records 审计表、sync_events 同步去重表。后台服务已启用云端读写，2 位现有飞书用户资料已同步，上线核查待同步数为 0，飞书长连接正常。原有业务表未修改。新脚本为 `docs/db/postgresql-v1.sql` 和 `docs/db/postgresql-v2.sql`；原 MySQL 脚本不适用于这次接入，保留不覆盖。

连接配置保存在被 Git 忽略的本机 `.env` 中，变量名 DATABASE_URL。`node scripts/db-check.mjs` 可只读检查连接和表清单，不输出密码。`node scripts/db-init.mjs` 仅用于首次建表，当前数据库已执行，勿重复运行。连接沿用用户给定的 sslmode=disable。

## 当前运行方式

本机 `.env` 的 DATABASE_ENABLED=true 启用 PostgreSQL；连接串使用 Node 支持的 postgresql:// 格式。运行适配器为 src/store-postgres.js。写入先落本机持久队列 data/postgres-outbox.json，再由单一消费者按顺序提交云端；同步成功后移除队列项。云端每次操作和去重回执在同一事务提交，提交响应丢失时重复补传不会重复入库。数据库离线时每 15 秒重试，不阻塞模型回答。

新聊天、回复、错误和工具审计写入 records；用户和助手正文同时写入 messages；用户资料、任务状态、会话重置、项目选择和附件位置写入对应表。/new 会归档云端旧会话，迟到回复仍通过原问题 ID 归属旧会话。原件和生成文件仍存本机，云端只存路径。解析状态暂未做完整的云端进度追踪。

运营看板从云端读取记录并与本机尚未同步的记录按 ID 合并，顶部显示云端连接及待同步数；用户资料可从云端恢复缓存。模型工作记忆、Codex 原生会话、项目本机配置、任务运行状态仍保留本机，数据库不是整台电脑的可直接替换备份。任务和会话映射会同步云端，但当前没有从云端重建整个运行目录的工具。

本次从启用时起同步新聊天，已有用户资料已同步。启用前的本机聊天和用户旧数据库的记录不会自动迁入新 messages 表，避免在无法还原 /new 边界时混入当前会话；旧数据仍按下文迁移方案另行导入。旧任务若没有云端原消息，其补发不会自动制造新的云端会话。

`npm test` 验证现有行为；`npm run test:postgres` 使用真实数据库外层事务，验证双用户隔离、复合外键、重置、迟到回复、重复事件、任务写入、离线重启、提交响应丢失后的重放和云端读取，最后回滚测试数据，不发飞书消息。上线已执行并通过。

## 身份与会话

用户唯一键为平台 + 飞书应用 ID + open_id，不按姓名识别人。一个用户在不同聊天、项目中有不同会话；同一个群的不同用户不会共享历史。助手消息也保存会话所有者的 user_id，发送角色另存 role。

`/new` 在事务中归档当前会话，再创建新的 active 会话。旧历史保留但不再自动送入模型。数据库的部分唯一索引限制同一用户、聊天、项目、助手只有一个活动会话；并发创建遇到唯一冲突时，应用重新读取已存在的会话。

## 表与用途

| 表 | 用途 |
|---|---|
| users | 飞书身份与基本资料缓存 |
| projects | 项目目录，空 ID 表示默认项目 |
| user_chat_settings | 每个用户在每个聊天中的当前项目 |
| conversations | 会话归属、项目、Codex 会话映射 |
| messages | 一行一条用户或助手消息，完整历史 |
| tasks | 执行状态、结果、发送进度与重试次数 |
| inbound_events | 飞书重复事件去重，跨新旧会话有效 |
| attachments | 私有上传和生成文件的归属、存储位置、解析状态 |
| legacy_imports | 旧数据暂存与幂等迁移记录 |

会话、消息、任务和附件通过包含 user_id 的复合外键防止错误跨用户关联。查询仍必须带当前已认证用户的 user_id 和 conversation_id；外键不是读取权限。当前方案未启用数据库行级权限，数据库业务账号仅供后台使用，不能直接交给普通用户。管理员的跨用户检索必须走独立鉴权入口。

项目公共资料仍由项目资料目录提供；私人附件不能作为项目公共资料同步。附件原件留在本机，数据库只存路径及元数据，storage_key 应是受控存储根目录内的相对路径。数据库备份不包含附件原件或本机 Codex 会话文件，需分别备份。Codex 登录凭据不入库。

## 旧表迁移规则

先原样保存到 legacy_imports.raw_record。以来源系统、表名、原 id 去重；确认原唯一用户的飞书身份后再生成业务消息。迁移和标记 imported 必须放在同一个事务，重跑时跳过 imported。

| 旧字段 | 新位置 |
|---|---|
| id | legacy_imports.source_id，另保留在消息 metadata |
| agent_id | conversations.agent_id |
| conversation_id | 作为旧会话映射依据，新会话使用应用生成的 UUID |
| message_id | messages.external_message_id，不能直接当内部主键 |
| role、content | messages.role、content |
| platform | users.platform，同时保留原始值 |
| status | 保留在 metadata.legacy_status，确认语义后再转换 |
| reply_content | 如果旧记录是一行一问一答，生成独立 assistant 消息并关联 reply_to_id |
| created_at | 原消息 created_at |
| replied_at | 拆出的助手消息 created_at；缺失时使用原创建时间并记录时间为推定 |

迁移前抽样确认旧表是否已经单独保存 assistant 行，避免把 reply_content 再导入成重复答案。每行原始数据完整保留，以便核对。

旧 conversation_id 必须与来源系统、原 agent_id 一起映射，不能直接复用以免不同来源撞号。无法确定 chat_id 时使用 `legacy:<来源>:<旧会话ID>`；导入会话全部设为 archived。无法确认用户身份的记录留在暂存表，不分配给新用户。历史迁移只导入消息，不创建待执行任务、不调用模型、不补发飞书消息。

核对暂存总数、成功/失败数、问答拆分条数、时间范围，并抽样比对正文与用户归属后才开放历史查询。旧表保留供核对，迁移不删除旧表。

## 接入步骤与运行约定

1. 配置现有数据库连接地址、端口、数据库名、业务账号及受信任的 TLS 证书；密码放本机环境配置。
2. 在目标数据库首次执行新 SQL，使用独立 requirement_assistant schema。脚本为事务性首次迁移，不使用 IF NOT EXISTS 掩盖同名结构冲突，重复执行会失败而不会覆盖。
3. 执行 v2 同步表迁移：node scripts/db-init.mjs --v2。当前已执行，适配器已启用并保留用户隔离检查。
4. 当前采用离线可运行模式：任务及消息先在本机持久化后开始模型处理，后台按顺序同步。消息与平台去重事件在云端同事务，任务快照为后续独立事务。结果先在本机保存再发送；重发只使用保存的结果，不重新执行模型。
5. 本机持久待同步队列已实现；断网在看板显示，按稳定 UUID 和事务回执幂等补传。数据库不可达时继续使用原有按用户隔离的本机缓存。
6. 已完成上述验证并切换后台服务。回退时停止服务、设 DATABASE_ENABLED=false 后重启即可；待同步队列须保留，以便重新启用时继续补传。

所有 UUID 由应用生成；时间使用带时区时间戳；updated_at 由应用每次更新时显式写入，不依赖自动触发器。运行中断任务标记 interrupted，不自动重新执行不确定是否完成的任务。消息历史默认不随本机日志的 90 天清理自动删除，保留期限需单独配置。

设计参考：[PostgreSQL 约束文档](https://www.postgresql.org/docs/current/ddl-constraints.html)。复合外键维护归属一致性，部分唯一索引限制活动会话数量。
