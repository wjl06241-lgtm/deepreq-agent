## 一、为什么这个数据库和你们之前建过的都不一样

### 1.1 一句话定义

这不是一个单纯的临床数据库升级，而是一个**临床数据与医保结算数据深度融合的"价值评价数据库"**——每个数据字段最终都要服务于国家医保局的7个评价维度。

### 1.2 和传统临床数据库的核心差异

| 对比维度 | 传统临床数据库（如现有DACCA） | 本项目要建的数据库 |
|---------|---------------------------|------------------|
| **数据来源** | HIS/EMR/手术记录/病理报告 | 上述 + **医保结算系统** + **耗材使用明细** + **DRG/DIP分组数据** |
| **主键设计** | 患者ID + 住院号 | 患者哈希ID + 住院流水号 + **手术记录ID** + **耗材流水号**（四级关联） |
| **字段设计逻辑** | 按临床诊疗流程组织 | 按**评价维度**组织——每个字段标注它服务的评价维度 |
| **核心产出** | 临床研究论文 | 真实世界评价报告 + **政策建议** + 方法学规范 |
| **数据更新模式** | 人工录入为主 + 定期批量导入 | **常态化ETL通道**——HIS/医保系统增量自动同步 |
| **横向比较能力** | 单病种纵向追踪 | 病种间/术式间/时间序列/人群间**多维交叉比较** |

### 1.3 你们需要理解的三个关键概念

**概念1：价值医疗四维度（我们的评价内核）**

我们团队已建立的价值医疗框架，将"医疗价值"拆解为四个可量化维度：

| 维度 | 通俗理解 | 数据对应 |
|------|---------|---------|
| 效果（医疗质量） | 治疗效果好不好？ | R0切除率、pCR率、生存率、复发率 |
| 风险（医疗安全） | 出了什么问题？ | 并发症分级、吻合口漏、LARS、死亡率 |
| 费用（医疗成本） | 花了多少钱？ | 住院总费用、耗材费用、DRG结余/超支 |
| 满意度（患者体验） | 患者满不满意？ | LARS评分、生活质量量表、满意度评分 |

**概念2：国家医保局7维度（政策评价外延）**

国家医保局在真实世界医保综合价值评价中要求7个维度，其中前4个和我们的四维度直接对应，后3个是新增的**政策评价维度**：

| 国家维度 | 对应我们的维度 | 新增？ | 数据来源要求 |
|---------|-------------|-------|------------|
| 有效性 | 效果 | 否 | 临床数据 |
| 安全性 | 风险 | 否 | 临床数据 |
| 经济性 | 费用 | 否 | **医保数据** |
| 患者体验 | 满意度 | 否 | 随访数据 |
| 公平性 | — | **新增** | **必须依赖医保数据**（医保类型、参保地、报销比例） |
| 可及性 | — | **新增** | **必须依赖医保数据 + 手术技术数据** |
| 创新性 | — | **新增** | 手术技术数据 + 耗材数据 |

> **关键理解**：公平性、可及性、创新性这三个维度是传统临床数据库无法评价的——因为它们需要医保结算数据（谁付了多少钱、什么医保类型、哪里来的患者）和手术技术细节数据（用了什么创新术式、什么耗材）。这就是为什么这个数据库必须融合医保数据。

**概念3：极限保肛手术（本数据库的核心创新聚焦点）**

| 术式 | 全称 | 通俗理解 |
|------|------|---------|
| ISR | 经括约肌间切除术 | 切除部分内括约肌，保留外括约肌——极限保肛 |
| ISR-A/B/C | ISR亚型 | A=部分内括约肌切除，B=次全切除，C=全切除——保留程度递减 |
| TaISLR | 经肛括约肌间切除重建术 | 华西团队原创术式 |
| taTME | 经肛全直肠系膜切除 | 从下方（经肛）做TME |
| LAR | 低位前切除术 | 常规保肛手术（对照组） |
| APR | 腹会阴联合切除术 | 不保肛，永久造口（对照组） |

> **为什么聚焦极限保肛**：因为APR（不保肛）和保肛手术在DRG支付中可能属于同一组、支付标准相同，但保肛手术技术难度更高、所需耗材更多——这导致医生缺乏做保肛手术的经济动力。我们就是要用真实世界数据证明保肛手术的"价值"更高，推动医保支付向保肛手术倾斜。这就是"未被满足的临床需求"（UMN）。

## 三、第一层：临床数据层升级——重点说清楚"新增了什么、为什么"

### 3.1 升级原则

**不推倒重来**。现有DACCA的9模块（1,237个数据元）保留，在其基础上：
- ALTER TABLE 新增字段（标注"新增"的）
- UPDATE 现有字段的约束/枚举值（标注"升级"的）
- 新建模块10（随访与预后强化）

### 3.2 关键新增字段说明（按模块）

#### 模块1（个人基本信息）——新增6个字段

| 新增字段 | 数据类型 | 枚举值/格式 | 为什么需要 |
|---------|---------|------------|----------|
| `insurance_type` | VARCHAR(20) | 城镇职工/城乡居民/自费/商业保险/其他 | **公平性维度核心字段**——不同医保类型的患者保肛率是否有差异？ |
| `insurance_region` | VARCHAR(50) | 成都市/四川省内其他市州/省外 | **可及性+公平性**——外地患者vs本地患者的术式选择差异 |
| `household_type` | VARCHAR(10) | 城市/农村 | **公平性**——城乡差异 |
| `first_visit_path` | VARCHAR(20) | 门诊/急诊/转诊/筛查 | **可及性**——首诊途径反映就医可及性 |
| `referral_source` | VARCHAR(50) | 本院门诊/下级医院转诊/外省就医 | **可及性+公平性**——转诊模式分析 |
| `patient_hash_id` | VARCHAR(64) | SHA-256哈希 | 脱敏主键，替代原始患者ID |

> **构建人员注意**：`insurance_type`和`insurance_region`这两个字段的值**既可能从HIS系统中获取（入院登记时记录），也可能需要从医保结算系统中匹配**。构建时需要与信息中心确认HIS入院登记是否已记录医保类型字段——如果已记录，直接从HIS取；如果未记录或不完整，需要从医保数据层反查。

#### 模块2（住院流程）——新增6个字段

| 新增字段 | 数据类型 | 说明 | 为什么需要 |
|---------|---------|------|----------|
| `admission_dept` | VARCHAR(50) | 入院科室 | **可及性**——不同科室收治的患者术式选择差异 |
| `attending_physician_hash` | VARCHAR(64) | 主诊医师哈希ID | **可及性**——技术可及性分析（哪些医师能做极限保肛） |
| `surgeon_hash` | VARCHAR(64) | 手术医师哈希ID | **可及性+创新性**——术式选择与医师的关联 |
| `is_planned_admission` | BOOLEAN | 计划性入院 vs 急诊入院 | **可及性** |
| `readmission_31d` | BOOLEAN | 出院后31天再入院 | **安全性+经济性**——再入院是质量指标 |
| `readmission_reason` | VARCHAR(50) | 并发症/肿瘤相关/其他 | **安全性** |

#### 模块6（手术特征）——★核心升级模块

这是整个数据库最重要的升级模块。现有DACCA模块6有手术基本信息，但缺少极限保肛手术的技术细节。

**6.1 需要新增到手术基本信息表的字段**：

| 新增字段 | 数据类型 | 枚举值 | 为什么需要 |
|---------|---------|-------|----------|
| `surgery_serial_no` | VARCHAR(32) | 手术流水号 | **关联医保数据的主键**——这是连接临床记录和医保耗材记录的桥梁 |
| `procedure_type` | VARCHAR(20) | LAR/ISR-A/ISR-B/ISR-C/TaISLR/taTME/APR/Hartmann/局部切除/其他 | **核心字段**——术式分类直接决定所有比较分析的分组逻辑 |
| `surgical_approach` | VARCHAR(20) | 开腹/腹腔镜/机器人辅助/经肛(taTME)/联合 | **可及性+创新性**——手术入路分析 |
| `surgery_urgency` | VARCHAR(10) | 择期/限期/急诊 | **安全性** |
| `conversion_flag` | BOOLEAN | 是否中转开腹 | **安全性+可及性**——中转率是技术可及性的逆向指标 |
| `conversion_reason` | VARCHAR(50) | 解剖困难/出血/肿瘤侵犯/设备故障/其他 | **安全性** |

**6.2 极限保肛专题数据集（新建子表）**——这是创新亮点，需要单独建表：

```sql
-- 极限保肛手术专题表
CREATE TABLE sphincter_preservation_detail (
    surgery_serial_no   VARCHAR(32) PRIMARY KEY,  -- 关联手术主表
    patient_hash_id     VARCHAR(64) NOT NULL,     -- 关联患者表
    -- 保肛决策
    preservation_basis  JSON,                      -- 保肛决策依据（数组：肿瘤距肛缘/括约肌功能/MRI/患者意愿/术者判断）
    sphincter_status    VARCHAR(30),               -- 完整保留/部分保留(内括约肌)/全切除
    isr_subtype         VARCHAR(10),               -- ISR-A/ISR-B/ISR-C（仅ISR术式填写）
    -- 吻合信息
    anastomosis_method  VARCHAR(30),               -- 手工吻合/圆形吻合器/直线切割吻合器
    stapler_brand       VARCHAR(30),               -- 强生/美外/康迪/瑞奇/其他
    stapler_model       VARCHAR(50),               -- 如圆形29mm/31mm/33mm
    icg_use             BOOLEAN,                   -- 是否使用ICG荧光造影
    icg_result          VARCHAR(30),               -- 血供良好/血供不佳(改变吻合方案)
    -- 平台与技术
    tatme_platform      VARCHAR(30),               -- GelPORT/SILS/其他（仅taTME填写）
    robot_assist        BOOLEAN,                   -- 是否机器人辅助
    -- 造口
    protective_stoma    BOOLEAN,                   -- 是否行保护性造口
    stoma_type          VARCHAR(30),               -- 末端回肠造口/袢式回肠造口/结肠造口
    stoma_reversal_days INTEGER,                   -- 造口还纳时间（天，NULL=未还纳）
    -- 手术质量
    specimen_quality    VARCHAR(20),               -- 完整/近乎完整/不完整（直肠系膜分级）
    circumferential_margin VARCHAR(10),            -- R0(>1mm)/R1(≤1mm)/R2(肉眼残留)
    distal_margin_mm    DECIMAL(5,1),              -- 远端切缘距离（mm）
    surgeon_self_eval   VARCHAR(10),               -- 优秀/良好/一般/差
    surgery_difficulty  JSON,                      -- 手术难度评分（各维度1-5分）
    -- 外键约束
    FOREIGN KEY (surgery_serial_no) REFERENCES surgery_main(surgery_serial_no)
);
```

> **构建人员注意**：
> 1. `stapler_brand`和`stapler_model`这两个字段的数据**可能需要从医保耗材明细中反查**——因为手术记录文本中不一定记录吻合器品牌型号，但耗材使用明细中一定有。这就是临床-医保数据融合的价值之一。
> 2. `surgery_difficulty`用JSON存储，包含6个子维度（解剖难度/骨盆条件/肥胖/粘连/系膜状态/脏器肥大），各1-5分。JSON格式便于后续灵活查询。
> 3. `preservation_basis`也是JSON数组，因为保肛决策可能基于多个因素。

**6.3 术式比较组设计**——数据库不需要物理实现比较组，但需要在视图层支持：

```sql
-- 示例：保肛vs APR比较视图
CREATE VIEW v_sphincter_vs_apr AS
SELECT
    s.surgery_serial_no,
    s.patient_hash_id,
    CASE
        WHEN s.procedure_type IN ('LAR','ISR-A','ISR-B','ISR-C','TaISLR','taTME') THEN 'sphincter_preservation'
        WHEN s.procedure_type = 'APR' THEN 'apR'
        ELSE NULL
    END AS group_assignment,
    s.procedure_type,
    s.surgical_approach,
    -- 有效性指标
    spd.circumferential_margin,
    CASE WHEN spd.circumferential_margin = 'R0' THEN 1 ELSE 0 END AS r0_flag,
    -- 安全性指标
    sc.anastomotic_leak_grade,
    -- 经济性指标
    m.total_cost,
    m.consumable_cost,
    -- 患者体验指标
    fu.lars_score_12m,
    fu.permanent_stoma
FROM surgery_main s
LEFT JOIN sphincter_preservation_detail spd ON s.surgery_serial_no = spd.surgery_serial_no
LEFT JOIN surgery_complication sc ON s.surgery_serial_no = sc.surgery_serial_no
LEFT JOIN m11_hospital_cost m ON s.admission_serial_no = m.admission_serial_no
LEFT JOIN m10_followup fu ON s.patient_hash_id = fu.patient_hash_id
WHERE s.procedure_type IN ('LAR','ISR-A','ISR-B','ISR-C','TaISLR','taTME','APR');
```

#### 模块10（随访与预后）——★强化模块

现有DACCA有随访模块，但缺乏多时间点的功能评价数据。本次升级重点：

| 新增/升级字段 | 数据类型 | 为什么需要 |
|-------------|---------|----------|
| `followup_timepoint` | VARCHAR(10) | 标准化随访时间点（1月/3月/6月/12月/24月/36月/60月） |
| `lars_score` | INTEGER | **患者体验核心指标**——LARS评分0-42分，各时间点分别记录 |
| `lars_grade` | VARCHAR(10) | 无LARS(0-20)/轻度(21-29)/重度(30-42) |
| `wexner_score` | INTEGER | 便秘评分0-20 |
| `qol_scale` | JSON | EORTC QLQ-C30 + QLQ-CR29量表结果 |
| `stoma_status` | VARCHAR(20) | 无造口/暂时性(已还纳)/永久性 |
| `satisfaction_score` | INTEGER | 1-10分 |
| `ctdna_mrd` | JSON | ctDNA/MRD监测结果+时间点 |

> **构建人员注意**：LARS评分是本数据库**患者体验维度的核心指标**。它不是一个总分，而是在术后1月、3月、6月、12月、24月、36月各有一个评分值。表设计上建议用 `(patient_hash_id, followup_timepoint)` 联合主键，每个时间点一行记录。

## 四、第二层：医保数据层——全新构建

### 4.1 这一层是整个项目的关键难点

这4个模块（M11-M14）是全新的，之前DACCA完全没有。数据需要从院内医保结算系统获取，**必须经过医保办授权**。

### 4.2 模块11：住院费用明细

```sql
CREATE TABLE m11_hospital_cost (
    admission_serial_no  VARCHAR(32) PRIMARY KEY,  -- 住院流水号（关联临床层）
    patient_hash_id      VARCHAR(64) NOT NULL,
    total_cost           DECIMAL(12,2),            -- 住院总费用
    drug_cost            DECIMAL(12,2),            -- 药品费用
```

## 五、第三层：价值评价层——视图设计

### 5.1 这一层不是物理表，是SQL视图

第三层不需要存储新数据，而是通过SQL视图（View）从第一层和第二层的表中计算得出。每个视图对应一个评价维度。

### 5.2 七个核心视图

| 视图名 | 对应维度 | 核心聚合逻辑 |
|-------|---------|------------|
| `v_effectiveness` | 有效性 | 按术式分组计算R0率、pCR率、复发率、DFS、OS |
| `v_safety` | 安全性 | 按术式分组计算吻合口漏率（A/B/C分级）、LARS率、并发症率、死亡率 |
| `v_economics` | 经济性 | 按术式分组计算费用均值/IQR、费用结构比、DRG结余/超支、ICER |
| `v_patient_experience` | 患者体验 | 按术式分组计算LARS评分变化、生活质量、造口状态、满意度 |
| `v_equity` | 公平性 | 按`insurance_type`×术式分组，计算保肛率差异、费用差异、自付比例差异 |
| `v_accessibility` | 可及性 | 按年度计算极限保肛开展率、APR率趋势、技术可及性logistic回归 |
| `v_innovation` | 创新性 | 按年度计算TaISLR/taTME/ICG/机器人开展率及效果 |

### 5.3 视图设计示例——公平性视图

```sql
CREATE VIEW v_equity AS
SELECT
    p.insurance_type,
    p.insurance_region,
    p.household_type,
    s.procedure_type,
    CASE
        WHEN s.procedure_type IN ('LAR','ISR-A','ISR-B','ISR-C','TaISLR','taTME') THEN '保肛'
        WHEN s.procedure_type = 'APR' THEN 'APR'
    END AS sphincter_group,
    COUNT(*) AS case_count,
    -- 保肛率
    ROUND(SUM(CASE WHEN sphincter_group = '保肛' THEN 1 ELSE 0 END) * 100.0 / COUNT(*), 1) AS sphincter_rate_pct,
    -- 费用
    ROUND(AVG(m.total_cost), 0) AS avg_total_cost,
    ROUND(AVG(r.personal_payment), 0) AS avg_personal_payment,
    ROUND(AVG(r.actual_reimb_ratio), 1) AS avg_reimb_ratio
FROM m1_patient p
JOIN surgery_main s ON p.patient_hash_id = s.patient_hash_id
JOIN m11_hospital_cost m ON s.admission_serial_no = m.admission_serial_no
JOIN m14_insurance_reimbursement r ON s.admission_serial_no = r.admission_serial_no
WHERE s.procedure_type IN ('LAR','ISR-A','ISR-B','ISR-C','TaISLR','taTME','APR')
GROUP BY p.insurance_type, p.insurance_region, p.household_type, s.procedure_type, sphincter_group;
```

> **构建人员注意**：这个视图的意义是——如果城镇职工的保肛率显著高于城乡居民，就说明存在"公平性"问题（经济条件好的患者更容易获得保肛手术）。这就是医保政策调整的证据基础。

| 比较组 | 暴露组 | 对照组 | 视图中的`group_assignment`逻辑 |
|-------|-------|-------|---------------------------|

## 六、ETL数据融合方案

### 6.1 数据流向

```
┌──────────┐     ┌──────────┐     ┌──────────┐
│  HIS系统  │     │ 医保结算  │     │  病理系统 │
│  (EMR)   │     │   系统    │     │  (PIS)   │
└────┬─────┘     └────┬─────┘     └────┬─────┘
     │                │                │
     ▼                ▼                ▼
┌──────────────────────────────────────────┐
│            ETL 中间层（脱敏+清洗+转换）     │
│                                          │
│  Step 1: 数据提取（Extract）               │
│    - HIS: 患者基本信息/住院记录/手术记录    │
│    - 医保: 费用明细/DRG分组/耗材明细/报销   │
│    - 病理: 病理报告/分期/分子分型           │
│                                          │
│  Step 2: 脱敏处理（Masking）               │
│    - 姓名/身份证/住院号 → SHA-256哈希      │
│    - 地址 → 区县级截断                    │
│    - 电话 → 删除                          │
│    - 医师姓名 → 编码化（医师A/医师B）       │
│                                          │
│  Step 3: 清洗与标准化（Transform）          │
│    - 枚举值标准化（如术式名称统一）          │
│    - 日期格式统一（YYYY-MM-DD）            │
│    - 数值范围校验（年龄0-120, BMI 10-60）   │
│    - 缺失值标记（NULL vs '未知' vs '未查'） │
│                                          │
│  Step 4: 关联与加载（Load）                │
│    - 患者哈希ID为主键关联各表               │
│    - 住院流水号关联临床+医保               │
│    - 手术流水号关联手术+耗材               │
│    - 加载到研究数据库                      │
└──────────────────────────────────────────┘
                    │
                    ▼
┌──────────────────────────────────────────┐
│            研究数据库（院内服务器）          │
│                                          │
│  第一层（临床）+ 第二层（医保）+ 第三层（视图）│
└──────────────────────────────────────────┘
```

### 6.2 关键ETL规则

| 规则 | 说明 | 实现方式 |
|------|------|---------|
| **主键对齐** | HIS的住院号和医保系统的住院号必须能匹配 | 用住院流水号作为跨系统关联键；需确认HIS和医保系统的住院号编码规则一致 |
| **脱敏一致性** | 同一个患者在HIS和医保系统中必须生成相同的哈希ID | 用身份证号作为哈希输入（SHA-256），确保跨系统一致 |
| **时间对齐** | 临床手术日期与医保结算日期可能不一致 | 允许±3天偏差；以临床手术日期为准 |
| **增量策略** | 新病例增量导入 | 每季度执行一次增量ETL，按出院日期筛选新增病例 |
| **冲突处理** | 同一字段在HIS和医保系统中值不一致时 | 临床字段以HIS为准，费用字段以医保系统为准，耗材品牌型号以医保明细为准 |

### 6.3 需要和信息中心确认的技术问题

| 序号 | 问题 | 影响 |
|------|------|------|
| 1 | HIS系统是否提供数据库直连接口或API？ | 决定ETL是数据库级别还是API级别 |
| 2 | 医保结算系统是否允许院内系统读取？需要什么授权？ | 决定医保数据层能否建立 |
| 3 | HIS和医保系统的住院号编码是否一致？ | 决定跨系统关联的可行性 |
| 4 | 病理报告是结构化数据还是文本？ | 决定是否需要NLP提取pTNM/CRM等字段 |
| 5 | 院内服务器是否能部署研究数据库？物理隔离要求？ | 决定数据库部署方案 |
| 6 | 是否有现成的数据脱敏工具？ | 决定脱敏是自己写还是用现成工具 |

## 八、数据质量标准——构建人员必须守住的红线

### 8.1 六维质量评估

| 质量维度 | 含义 | 评估方法 | 合格标准 | 不合格怎么办 |
|---------|------|---------|---------|------------|
| **完整性** | 关键字段非空率 | 各模块核心字段缺失率统计 | 核心字段缺失率<5% | 标注缺失原因；评估是否影响分析 |
| **一致性** | 临床-医保数据交叉一致 | 患者ID/住院号/手术日期跨源比对 | 一致率>95% | 查找冲突原因；以规则确定优先源 |
| **准确性** | 数据与原始记录符合度 | 每模块随机抽50例与病历比对 | 准确率>90% | 修正ETL规则；重新清洗 |
| **时效性** | 数据更新频率 | 最后更新日期距今天数 | 增量更新≤季度 | 建立自动ETL调度 |
| **唯一性** | 无重复记录 | 患者ID+住院号+手术号联合唯一性检查 | 重复率<0.1% | 去重；查ETL去重逻辑 |
| **合理性** | 数值在临床合理范围 | 逻辑校验规则 | 异常率<1% | 逐条核查异常值 |

### 8.2 融合质量专项指标

| 指标 | 含义 | 合格标准 | 不合格的影响 |
|------|------|---------|------------|
| 临床-医保匹配率 | 临床记录能匹配到医保结算记录的比例 | >90% | 医保维度评价样本量不足 |
| 耗材-手术匹配率 | 耗材记录能匹配到手术记录的比例 | >85% | 耗材评价无法进行 |
| 随访-再入院匹配率 | 随访记录能匹配到再入院记录的比例 | >80% | 长期结局评价不完整 |
| 时间一致性 | 临床手术日期与医保结算日期偏差 | ±3天内 | 时间序列分析误差 |

### 8.3 质量评估自动化

```sql
-- 示例：数据质量评估脚本
-- 完整性检查
SELECT
    'M1_个人基本信息' AS module,
    'insurance_type' AS field,
    COUNT(*) AS total,
    SUM(CASE WHEN insurance_type IS NULL THEN 1 ELSE 0 END) AS null_count,
    ROUND(SUM(CASE WHEN insurance_type IS NULL THEN 1 ELSE 0 END) * 100.0 / COUNT(*), 1) AS null_rate_pct
FROM m1_patient
UNION ALL
SELECT
    'M6_手术特征' AS module,
    'procedure_type' AS field,
    COUNT(*) AS total,
    SUM(CASE WHEN procedure_type IS NULL THEN 1 ELSE 0 END) AS null_count,
    ROUND(SUM(CASE WHEN procedure_type IS NULL THEN 1 ELSE 0 END) * 100.0 / COUNT(*), 1) AS null_rate_pct
FROM surgery_main
-- ...其他字段
;
```

## 九、数据安全与脱敏

### 9.1 脱敏规则（必须在ETL层完成，原始数据不进研究库）

| 原始字段 | 脱敏方法 | 说明 |
|---------|---------|------|
| 姓名 | SHA-256哈希 | 不可逆，跨系统一致 |
| 身份证号 | SHA-256哈希 | 不可逆，作为哈希ID生成源 |
| 住院号 | SHA-256哈希 | 院内可追溯但不可逆向 |
| 住址 | 区县级截断 | 只保留到区/县 |
| 电话 | 删除 | 不保留 |
| 医师姓名 | 编码化 | 如"医师A"/"医师B"，映射表由试点负责人保管 |
| 耗材品牌 | **保留** | 经济性评价需要（不同品牌价格不同） |

### 9.2 访问控制

| 角色 | 权限 | 说明 |
|------|------|------|
| 数据库管理员 | DDL+DML | 建表、ETL运维，**不可查看研究数据内容** |
| 数据分析师 | SELECT | 全部脱敏后数据查询权限 |
| 试点负责人 | SELECT+审计日志 | 全部数据+操作审计 |
| 医保办对接人 | SELECT | 全部脱敏后数据 |
| 信息中心 | 仅ETL通道运维 | **不可见原始研究数据** |

### 9.3 物理部署

- 研究数据库部署在**院内服务器**，物理隔离，不外传
- 分析工作在院内完成，**数据不出院**
- 所有数据访问操作记录审计日志
- 定期备份，备份文件加密存储

## 十一、常见问题预判

### Q1：吻合器品牌型号在手术记录里没有怎么办？

**A**：这是预期中的问题。手术记录文本中通常只写"使用圆形吻合器完成吻合"，不记录品牌型号。但医保耗材明细中一定有（因为需要计费）。处理方式：
1. 从M13（耗材明细）中按`surgery_serial_no`关联，反向填充M6专题表的`stapler_brand`和`stapler_model`
2. 如果手术记录中没有`surgery_serial_no`，用`admission_serial_no`+手术日期范围模糊匹配耗材记录

### Q2：DRG分组数据在医保系统还是HIS系统里？

**A**：DRG分组通常由医保结算系统在出院结算时生成，HIS系统中可能只有DRG编码（如有），完整分组信息（权重、支付标准）在医保系统中。需要与医保办确认数据获取方式。

### Q3：2018年以前的医保数据能回溯吗？

**A**：取决于医保系统的数据保留策略。一般医保结算系统保留5-10年。建议：
1. 先确认医保系统最早可回溯到哪一年
2. 如果只能回溯到2020年，则2020年以前的病例只有临床数据、无医保数据——标注为"部分融合"
3. 不影响分析——PSM配平时可按数据完整性分层

### Q4：LARS评分在现有DACCA里有吗？

**A**：可能部分有，但不系统。LARS评分是术后功能评价的核心指标，需要在多个时间点（1/3/6/12/24/36月）分别采集。如果现有随访数据中缺乏LARS评分：
1. 回溯性数据标注为"缺失"——不影响数据库构建，但影响患者体验维度的评价能力
2. 前瞻性纳入的新病例必须采集LARS评分

### Q5：数据库用什么技术栈？

**A**：建议根据院内现有条件选择：

| 方案 | 适用场景 | 优点 | 缺点 |
|------|---------|------|------|
| PostgreSQL | 数据量<100万行 | 开源免费、JSON支持好、视图功能强 | 大数据量性能需优化 |
| MySQL | 院内已有MySQL环境 | 运维熟悉 | JSON支持不如PG |
| SQL Server | 院内已有SQL Server | 企业级稳定 | 授权费用 |

建议优先使用**PostgreSQL**——JSON字段、物化视图、窗口函数等特性最适合本项目的视图层需求。
