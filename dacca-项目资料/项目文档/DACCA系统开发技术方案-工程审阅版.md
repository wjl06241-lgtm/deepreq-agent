## 1. 范围与本轮边界

### 1.1 本轮做什么

1. 建立 PostgreSQL 星型事实库作为唯一真相源。
2. 建立接入层：staging、字段映射、值域清洗、身份链接候选、质量闸门。
3. 建立治理层：DQ 规则引擎、异常日志、完整度评分、治理任务队列、审计。
4. 建立规则引擎：派生标签由版本化规则计算，不硬编码。
5. 建立服务层与前端治理工作台，让医疗团队能实际治理数据。
6. 建立数据集市与基础统计（Table 1 / KM / Cox / 队列筛选）。
7. 事件溯源 sidecar 与图谱派生作为增强能力，按 Sprint 排期。

### 1.2 本轮不做什么（已确认延后）

| 项 | 决定 |
|---|---|
| 八大应用场景铺开（药企 RWE、器械 RWE、医保价值医疗、商保、患者管理、专病大模型对外供给、多中心/区域 RWD） | **放到下一阶段**。本轮只保证底层原子事实齐备、视图可派生，不建场景专用表、不做对外交付 |
| 对外患者级数据交付 | 不做 |
| 临床录入主系统切换 | 不做，旧库继续承担录入 |
| 自动患者管理推送、保险自动核保 | 不做 |

**本轮的应用出口只有两个**：院内数据治理、科研队列与统计分析。

### 1.2.1 本轮纳入一个应用场景：器械与术式 RWE（极限保肛专题）

医疗团队要求本轮介入一个应用场景。经比选，**推荐「器械与术式真实世界研究」，以极限保肛（ISR / TaISLR / taTME vs APR）为切入专题**。

**为什么选它 —— 五个场景的可行性比选**

| 候选场景 | 外部依赖 | 字段就绪度 | 本轮可行 |
|---|---|---|---|
| 药企 RWE | 无授权依赖，但**对外交付本轮排除** | 分子/用药/疗效已设计，但存量分子数据可能稀疏 | ⚠️ 只能做内部视图，价值打折 |
| 医保价值医疗 | **卡医保办授权 + 费用类目对齐** | M11-M14 未建 | ❌ 硬阻塞 |
| 商保带病体 | 依赖费用数据 → 间接卡医保 | 部分缺失 | ❌ 阻塞 |
| 患者全生命周期 | LARS 存量在研究组、需迁移对齐 | 部分就绪 | ⚠️ 需等样例 |
| **器械与术式 RWE** | **无任何外部授权依赖** | **手术方式、入路、吻合、造口、保肛意愿、CD 并发症、R0/CRM 团标全覆盖** | ✅ **立即可做** |

**选它的四条理由**

1. **零外部依赖**：所需字段全部来自院内既有手术与病理记录，不需要医保办授权、不需要外部数据源、不需要等研究组交表。
2. **字段已定稿**：手术方式代码表、手术路径、吻合口质量评估、肠造口术类型、造口原因、还瘘日期、保肛意愿类型、术后排便评估、并发症+CD 分级、R0/CRM——团标与历轮讨论已全部覆盖，不必新造字段。
3. **它是真实的业务落点**：极限保肛 vs APR 的价值证明，是医疗团队既定的核心命题，将来还要用于推 DRG 支付分组。本轮先把数据链路跑通，下一阶段医保授权到位即可直接接经济性维度。
4. **它能完整压测架构**：这个场景要串起「手术事实 → 并发症事件 → CD 分级推导 → 功能结局 → 生存结局」整条链，正好检验规则引擎、事件级记录、时序推导是否真的站得住。比只做治理和统计更能暴露设计缺陷。

**本轮该场景交付什么**

- 一张「术式对比队列视图」：按术式分组，输出病例数、R0/CRM 达标率、并发症谱与 CD 分级分布、造口率与还纳率、住院天数。
- 该视图**从底层事实派生**，不建场景专用表——用于验证"场景是视图不是表"这条通则。
- 不做对外交付，仅供院内科研分析使用。

**边界**：本场景不含费用与经济性分析（属医保层，下一阶段）；不含 LARS 功能结局（等研究组样例，届时作为该场景的功能维度补入）。

### 1.3 数据供给的正确定义（重要）

"数据供给"指的是**把数据灌进本库用于测试与验证**，不是对外供数。因此以下四项是**入库数据的方式、规则与边界**，落地为 `dim_patient` / `event_store` 上的治理属性字段，不是新场景：

| 项 | 性质 | 落地位置 |
|---|---|---|
| 向量化状态 | 这条数据是否已被向量化、用哪个模型、什么版本 | 治理元数据字段 |
| AI 训练许可 | 这条数据是否允许用于模型训练 | 授权字段，默认否 |
| 数据护照 | 这批数据的来源、授权、脱敏级别、可用范围的凭证记录 | `data_passport` 表 |
| 授权范围 | 这条/这批数据被授权用于哪些用途（治理/科研/训练/导出） | 授权字段，按批次与患者双层控制 |

## 2. 术语与口径基线

| 术语 | 定义 |
|---|---|
| 原子事实 | 直接观测或记录到的、不含推断的最小事实单元（如"某日检出肝转移"） |
| 派生标签 | 由原子事实经版本化规则计算得到的结论（如"异时性转移"） |
| SoR | System of Record，唯一真相源，本项目指 PostgreSQL 星型库 |
| 血缘 | 一条数据从源文件某行某列到入库值的完整可追溯链 |
| 身份链接 | 判断多条记录是否属于同一患者的过程 |
| 治理 | 对低质量数据进行人工核查与修正，并留下审计痕迹 |
| 数据护照 | 一批数据的来源、授权、脱敏级别、可用范围的凭证记录 |

## 2A. 本体论：本项目所有结构设计的依据

> 本章解释**为什么表结构必须长成第 5 章那个样子**。工程实现中遇到设计取舍时，回到本章判断。
> 不理解这一层，后续所有规定都会变成难以理解的教条，遇到具体问题时容易凭直觉走偏。

### 2A.1 什么是本体

本体论（Ontology）源自哲学，研究"**存在什么**"。用于数据建模时，它回答三个问题：

1. 这个领域里客观存在哪些**实体**
2. 每个实体有哪些**属性**
3. 实体之间是什么**关系**

**关键在"客观"二字：本体描述的是这个领域里有什么，而不是我们想拿它做什么。**

### 2A.2 DACCA 的本体构成

| 层面 | 内容 |
|---|---|
| **实体** | 患者、肿瘤、手术、病理、分子检测、用药、放疗、并发症、不良事件、复发转移、随访、功能评价、合并症 |
| **属性** | 肿瘤有部位、距肛缘距离、分期；手术有术式、入路、吻合方式；用药有剂量、线数、起止日期 |
| **关系** | 一个患者可有多个肿瘤（多原发）；并发症依附于某次手术；不良事件依附于某次用药；病理来自某次手术的标本 |

`dim_tumor` 独立于 `dim_patient` 存在，正是本体决定的——**医学上"人"和"瘤"本就是两个不同的东西**，不是为查询方便而设计的中间层。

### 2A.3 判定标准：什么属于本体，什么不属于

判断某个东西是否属于本体，问一句：**它是否独立于任何应用场景而存在？**

| 对象 | 属于本体？ | 判定理由 |
|---|---|---|
| 肿瘤部位 = 直肠 | ✅ 是 | 不论谁查、是否有人查，它客观存在 |
| 转移灶首次检出日期 | ✅ 是 | 客观发生过的事件 |
| 手术使用腹腔镜入路 | ✅ 是 | 客观事实 |
| "异时性转移" | ❌ 否 | 取决于采用 6 个月还是 12 个月口径——是**结论**不是事实 |
| "高危患者" | ❌ 否 | 取决于谁定义的高危标准——是**规则产出** |
| "药企 RWE 队列" | ❌ 否 | 取决于药企需要什么——是**视图** |
| "满意度评分" | ❌ 否 | 不可核验、不可复现（见 12.2 准入线） |

### 2A.4 本体 / 规则 / 视图：三层关系

项目中反复出现的三个概念，边界如下：

| 层 | 回答什么 | 示例 | 稳定性 |
|---|---|---|---|
| **本体层** | 客观发生了什么 | 手术日 2024-03-15；转移灶检出日 2024-11-20 | **不变** |
| **规则层** | 这些事实意味着什么 | 间隔 8 个月 ≥ 阈值 6 个月 → 异时性 | 会变（阈值可换） |
| **视图层** | 谁从什么角度看 | 医保按 7 维度切；药企按人群-暴露-结局切 | 经常变 |

项目三条核心原则，正是这三层各一条：

| 原则 | 守护的层 |
|---|---|
| 只存原子事实 | 本体层不被结论污染 |
| 标签可推导、规则带版本 | 规则层独立可换 |
| 场景是视图不是表 | 视图层不得污染下两层 |

### 2A.5 为什么这件事在工程上至关重要

**因为"客观有什么"是稳定的，"怎么记录、怎么使用"是易变的。**

| 变化 | 影响记录方式 | 影响客观事实 |
|---|---|---|
| 医院更换 HIS | 文书格式全变 | 患者做了什么手术**没变** |
| 接入新中心 | Excel 表头完全不同 | 肿瘤长在哪里**没变** |
| 新增应用场景（商保、卫健委考核） | 需要新的视图 | 底层事实**一条没变** |
| 临床指南更新 | 判定口径改变 | 观察到的检查结果**没变** |

**把数据库建在稳定的东西上，才能不推倒重来。** 这正是北极星"好的数据结构能满足尽可能多的研究口径"背后的机制——口径是变的、事实是不变的，按事实建库，口径便可任意切分。

### 2A.6 两个典型的反本体设计（本项目明令禁止）

| 错误做法 | 它反映的是什么 | 后果 |
|---|---|---|
| **按文书类型建表**（fact_surgery_record、fact_pathology_report） | 别人**怎么记录** | 换数据源即失效；同一事实被劈散（见 6C.11） |
| **按场景建表**（药企患者表、医保患者表） | 我们**想怎么用** | 同一属性多处存储、口径打架；新场景又要新建表（见 5.6） |

二者本质是同一个错误：**把易变的东西当作了地基**。

### 2A.7 与启动细则的对应

启动细则原则 1 "表结构必须围绕结直肠癌真实诊疗过程中的医学实体、事件和关系设计，而不是简单复刻 Excel 表头"——即本章所述内容的另一种表述。

### 2A.8 工程实践中的应用

遇到以下情形时，回到本章判断：

| 情形 | 判断方法 |
|---|---|
| 该不该为某需求新建表 | 它是新的**医学实体**，还是某个场景的**视图**？后者不建表 |
| 某字段该放哪张表 | 这个属性属于**哪个实体**？（如 ECOG 随时间变化 → 属于随访事件，不属于患者） |
| 该建物理列还是走规则 | 它是**观察到的**，还是**推断出的**？后者不建列 |
| 两个概念该合并还是分开 | 医学上是**同一个东西**吗？（如 cCR 与 pCR 判定依据不同 → 必须分开） |

## 3. 系统总体架构

### 3.1 五层架构与工程七层的映射关系

对外沟通用五层，工程施工按 E0-E6 拆任务，两者是同一套系统的两种切法：

```
对外五层                      工程施工层
─────────────────────────────────────────────
L5 应用层        ←──────→    E6 应用与运营层
L4 服务层        ←──────→    E5 服务与安全层
L3 语义层        ←──────→    E4 语义与数据集市层
L2 星型事实层    ←──────→    E2 星型事实存储层
                             E2b 事件溯源 sidecar
                             E3 治理与合规层（横切 L1-L4）
L1 接入主索引层  ←──────→    E1 接入与主索引层
                             E0 数据源层
```

注意 **E3 治理层是横切的**，不对应单一业务层——它的表（审计、规则注册、异常日志）服务所有层。

### 3.2 数据流主链路

```
源文件/源系统
  │
  ├─ E0: 登记 source_batch_registry（批次号 + 文件哈希）
  ↓
staging 原样落地（不做任何转换，保留原始值）
  │
  ├─ E1: field_mapping_registry 字段映射
  ├─ E1: value_domain_registry 值域清洗
  ├─ E1: identity_linkage_map 身份链接（确定性自动 / 模糊仅候选）
  ├─ E1: 事件锚定（挂到 patient_id + event_date）
  ├─ E1: 质量闸门（不合格进隔离区，不进真相源）
  ↓
E2: 星型事实库（dim_patient + fact_*）  ← 唯一真相源
  │
  ├─ E2b: 复杂上下文进 event_store（JSONB）
  ├─ E3: DQ 规则扫描 → dq_exception_log → 完整度评分 → 治理任务队列
  ↓
E4: 规则引擎计算派生标签 → mart_* 数据集市 → Neo4j 派生
  ↓
E5: API 服务（权限 / 脱敏 / 审计）
  ↓
E6: 治理工作台 / Dashboard / 科研分析
```

### 3.3 三条架构不变量

工程实现中任何设计都不得违反：

1. **单向派生**：数据只在星型库落地一次。event_store、mart、Neo4j 全部是派生物，可从星型库重建，不反写。
2. **事实与结论分离**：`fact_*` 表只存原子事实；所有临床结论走规则引擎产出，带 `rule_version_id`。
3. **血缘不可断**：任何入库值必须能回溯到 source_file + sheet + row + column。断链即视为缺陷。

## 4. 技术栈与选型说明

| 层 | 技术 | 版本 | 选型理由 |
|---|---|---|---|
| 主数据库 | PostgreSQL | 16+ | 事务、审计、分区、JSONB、权限成熟；需要 JSONB 存事件包，同时要强一致的明细事实 |
| ORM / 迁移 | SQLAlchemy 2.x + Alembic | — | 表结构变更必须 migration 化，可回滚可审计 |
| 后端 | Python + FastAPI | 3.11+ | 与数据处理、统计生态同语言，减少跨语言成本；自带 OpenAPI |
| 数据处理 | Pandas + psycopg2 | — | ETL、清洗、批处理 |
| 统计分析 | lifelines / tableone / scipy | — | KM、Cox、Table 1，临床统计标准库 |
| 前端 | Vite + React + TypeScript | — | 治理工作台是高频表单场景，需要 schema-driven 动态渲染 |
| 样式 | Tailwind | — | — |
| 图表 | Recharts | — | 大盘、KM 曲线 |
| 图数据库 | Neo4j | — | **只读派生**，表达实体关系，不存明细 |
| 本地 AI | Ollama / 本地模型 | — | 仅候选抽取与映射建议，不参与决策；明文数据不出内网 |
| 部署 | 内网服务器 + Docker Compose | — | 患者数据绝对隐私，必须私有部署 |

### 4.1 关键选型约束

- **不引入云托管数据库**：患者明文数据不出内网，这是硬约束。
- **不引入第三方 SaaS 分析平台**：同上。
- **Neo4j 版本选择**：社区版即可满足本轮（只读派生、单实例）。若未来需要因果集群或细粒度权限再评估企业版。
- **AI 相关**：只允许本地/内网模型；云端模型仅可接触 schema、枚举、值域说明，不可接触患者数据。

## 5. 数据库设计

### 5.1 表分组总览

| 组 | 表 | 作用 |
|---|---|---|
| 维度 | `dim_patient` | 患者唯一锚点 + 共享分层轴 |
| 事实 | `fact_clinical_event` `fact_tumor_pathology` `fact_treatment_outcomes` `fact_followup_event` `fact_molecular` `fact_medication` `fact_response_assessment` `fact_adverse_event` `fact_complication` `fact_metastasis` `fact_functional_assessment` | 原子事实 |
| 事件溯源 | `event_store` | 复杂上下文事件包（JSONB） |
| 接入 | `staging_*` `source_batch_registry` `field_mapping_registry` `value_domain_registry` `identity_linkage_map` | 接入与映射 |
| 治理 | `meta_data_governance` `dq_rule_registry` `dq_exception_log` `audit_log` `data_passport` | 质量与合规 |
| 规则 | `rule_version_registry` `derivation_rule_registry` | 派生规则与版本 |
| 集市 | `mart_patient_summary` `mart_cohort_*` | 统计宽表 |
| 系统 | `sys_users` `sys_roles` | 权限 |

### 5.2 dim_patient —— 唯一锚点与共享分层轴

**设计原则**：所有分层变量沉淀在此，各场景取同一份数据的不同列，禁止为某场景新建患者表。

| 字段组 | 字段 | 说明 |
|---|---|---|
| 主键 | `patient_id` | UUID5 或确定性哈希，不暴露明文身份 |
| 身份（受控） | `id_card_hash` `hospital_no` | 哈希存储，明文访问需 raw 权限 |
| 人口学 | `gender` `birth_date` `age_at_diagnosis` | — |
| 临床分层 | `ecog_ps` `charlson_index` | 合并症明细在 fact 表，此处存指数 |
| 医保分层 | `insurance_type` `insured_region` `urban_rural` | **下一阶段启用**，本轮建字段留空 |
| 治理属性 | `data_completeness_score` `governance_status` | 由规则计算 |
| 授权属性 | `ai_training_permitted` `authorized_scope` `vectorization_status` | 入库数据的边界控制（见 1.3） |
| 血缘 | `source_batch_id` `created_at` `updated_at` | — |

### 5.3 事实表通用规范

每张 `fact_*` 表必须包含：

| 字段 | 说明 |
|---|---|
| `patient_id` | 外键，锚点 |
| `event_id` | 由 patient_id + event_date + event_type 确定性生成 |
| `event_date` | 事件发生日 |
| `source_record_id` | 文件名 + sheet + row + hash |
| `source_batch_id` | 批次 |
| `source_system` | HIS / Excel / 人工录入 / 研究组表 |
| `raw_value` / `cleaned_value` | 原始值与清洗后值（关键字段） |
| `mapping_rule_id` `rule_version` | 映射规则与版本 |
| `data_status` | 实测 / 推断 / 预测 / 人工修正 / AI提取 |
| `confidence` | 置信度 |
| `extracted_by_ai` `review_status` `reviewed_by` `reviewed_at` | AI 产出审计 |

### 5.4 关联键设计

主锚点是 `patient_id`，业务流水号只作关联键补挂：

```
dim_patient (patient_id)
   ├── fact_clinical_event (event_id, admission_no?)
   ├── fact_treatment_outcomes (surgery_no?)
   ├── fact_complication (surgery_no → 关联到具体手术)
   ├── fact_functional_assessment (surgery_no → 算距术天数)
   └── ...
```

`admission_no`（住院流水号）、`surgery_no`（手术流水号）用于把费用、耗材、并发症、功能评价挂到正确粒度，**不替代 patient_id 作为主锚点**。

### 5.5 JSONB 使用边界

**允许**：原始事件包、复杂上下文、AI 提取候选、来源字段快照、暂未标准化的扩展属性。

**禁止长期只放 JSONB 的核心字段**（必须结构化并建索引）：
T / N / M 分期、MSI、MMR、KRAS、BRAF、手术日期、生存状态、死亡日期、复发转移日期、费用、随访日期、CD 分级。

判断标准：**应用层会用来筛选的字段，一律结构化**。

### 5.6 字段扩展机制

新增字段按此顺序判断，严禁为某场景新建患者表：

1. 是否已有实体的新属性 → 加列
2. 是否已有事件的新事实 → 加列
3. 是否派生标签 → 进规则引擎，不落物理列
4. 是否应用视图字段 → 进 mart / view
5. 确需新实体 → 新建 fact 表

所有结构化新增必须同步：Alembic migration、数据字典、中文释义、值域单位、来源与治理规则、是否参与评分/筛选/脱敏/导出。

## 6. 规则引擎设计（本方案的技术核心）

这是"事实与结论分离"落地的地方，也是工程上最容易做错的部分。

### 6.1 为什么必须做成引擎而不是硬编码

临床口径会变。如果把"异时性转移 = 间隔 ≥6 个月"写进 SQL 或 Python 里，那么将来口径改成 12 个月时，必须改代码、重跑、且**历史结果无法复现**。做成引擎后，改的是规则表里的一行参数，重算即可，底层事实不动。

### 6.2 规则注册表结构

`derivation_rule_registry`：

| 字段 | 说明 |
|---|---|
| `rule_id` | 规则标识，如 `METASTASIS_TIMING` |
| `rule_version_id` | 版本号，每次变更递增 |
| `rule_name_cn` | 中文名 |
| `input_fields` | 依赖哪些原子事实字段 |
| `parameters` | JSONB，可配置参数（阈值、锚点等） |
| `logic_expr` | 规则表达式或函数引用 |
| `output_field` | 产出标签名 |
| `effective_from` / `effective_to` | 生效区间 |
| `approved_by` / `approved_at` | 医疗团队审核人（规则上线必须医工共同确认） |

### 6.3 规则执行方式

两种模式，按字段使用频率选择：

| 模式 | 适用 | 实现 |
|---|---|---|
| 实时计算 | 低频、明细查询 | 查询时由规则引擎计算，视图中体现 |
| 物化 | 高频筛选、统计 | 写入 `mart_*`，带 `rule_version_id`；规则变更时重算 |

**物化结果必须可重建**，且必须记录用哪个版本算的。

### 6.4 本轮必须实现的派生规则清单

| 规则 | 输入原子事实 | 参数 | 产出 |
|---|---|---|---|
| 转移时序判定 | 原发灶手术日、转移灶首检日、初诊 M 分期 | 基准日锚点=手术日、阈值=6个月 | 同时性 / 异时性 |
| CD 分级推导 | 并发症干预措施（用药/输血/内镜/介入/再手术/ICU/器官衰竭/死亡） | 干预阶梯映射表 | I / II / IIIa / IIIb / IVa / IVb / V |
| pCR 判定 | 病理学肿瘤消退分级 TRG | TRG=0 即 pCR | pCR 是/否 |
| LARS 分级 | 各条目原始得分 | 总分阈值分档 | 无 / 轻度 / 重度 |
| OS | 手术日或确诊日、末次随访日、生存状态 | 起算锚点可配 | 天数 + 删失标记 |
| DFS | 手术日、复发转移日、末次随访日 | — | 天数 + 删失标记 |
| PFS | 治疗起始日、疾病进展日 | 起算锚点可配 | 天数 + 删失标记 |
| 完整度评分 | 各字段填充状态 | 字段权重表 | 0-100 分 |

**注意**：转移时序、pCR、LARS 三条的医学口径见第 12 章，参数已由医疗团队拍板，工程实现时按那里的口径配置。

## 6A. 字段元数据注册表（字段可扩展 + AI 字段理解的共同底座）

> 医疗团队提出两个需求：①字段要能编辑增减、对表做扩充；②医生录入时希望 AI 能识别匹配字段内容。
> 这两件事在工程上依赖同一个设施——**字段元数据注册表 `field_registry`**。没有它，字段加不动，AI 也无从判断一段文字该进哪个字段。本章统一设计。

### 6A.1 核心问题：为什么不能直接改表

直接 `ALTER TABLE` 加列会带来三个问题：

1. 加了列，但**没人知道它是什么意思**——没有中文释义、没有值域、没有单位，下一个人不敢用。
2. 前端表单**不会自动出现这个字段**，得改前端代码。
3. AI **不知道这个字段存在**，更不知道什么样的文字该填进去。

所以字段扩展不是一个 DDL 动作，而是一个**注册动作**：物理列 + 元数据 + 前端渲染 + AI 识别依据，四者同时生效。

### 6A.2 field_registry 表设计

这是全库字段的唯一说明书，前端渲染、AI 识别、数据字典、导出控制全部读它：

| 字段 | 说明 |
|---|---|
| `field_id` | 唯一标识 |
| `table_name` / `column_name` | 物理位置 |
| `field_name_cn` | 中文名（前端标签） |
| `definition` | 医学定义（AI 语义匹配的主要依据） |
| `synonyms` | JSONB，同义词/别名/常见写法（如"吻合口瘘"↔"吻合口漏"） |
| `data_type` | 类型 |
| `value_domain_id` | 关联值域表，枚举字段的可选值 |
| `unit` | 单位 |
| `is_required` | 是否必填 |
| `is_derived` | **是否派生字段**（是则不可人工录入，由规则引擎产出） |
| `derivation_rule_id` | 派生字段对应的规则 |
| `authority_source` | 权威源：system / expert（见 12.1 仲裁原则） |
| `ui_widget` | 前端控件类型：文本/下拉/多选/日期/数值 |
| `ui_group` / `ui_order` | 前端分组与排序 |
| `ai_extractable` | **是否允许 AI 抽取填充** |
| `ai_hint` | 给 AI 的提示（该字段典型表述、注意事项） |
| `participates_in_score` | 是否参与完整度评分 |
| `masking_level` | 脱敏级别 |
| `exportable` | 是否允许导出 |
| `status` | draft / active / deprecated |
| `version` / `created_by` / `approved_by` | 版本与审批 |

### 6A.3 字段扩展的标准流程

新增或修改字段走统一流程，**禁止绕过注册表直接改库**：

```
医疗团队提出字段需求
  ↓
按 5.6 判断归属（已有实体属性？新事实？派生标签？视图字段？新实体？）
  ↓
在 field_registry 登记（status=draft，填中文名/定义/值域/单位/AI提示）
  ↓
医疗团队审核医学含义与值域 → approved_by
  ↓
工程生成 Alembic migration（物理列）
  ↓
dev 测试 → staging 验证 → 备份后 production
  ↓
status=active
  ↓
前端表单自动渲染（schema-driven，无需改前端代码）
AI 抽取自动纳入该字段（读 definition + synonyms + ai_hint）
数据字典自动更新
```

**关键设计：前端 schema-driven。** 治理工作台的表单不是写死的，是启动时读 `field_registry` 动态渲染。所以字段注册完成后，前端**不需要发版**就能显示新字段。这是"字段能编辑增减"的工程前提。

### 6A.4 三种扩展类型的不同处理

| 类型 | 处理 | 是否需要 migration |
|---|---|---|
| 已有实体加属性 | field_registry 登记 + 加列 | 是 |
| 派生标签 | 只登记规则（derivation_rule_registry），**不加物理列** | 否 |
| 暂未标准化的扩展属性 | 先进 event_store JSONB，成熟后再结构化 | 否（后续结构化时才需要） |

第三种是缓冲机制：医生临时需要记录某项内容、但字段定义还没想清楚时，先落 JSONB 保住数据，不阻塞临床，等定义清晰再提升为正式字段。**但核心字段（TNM、MSI、KRAS、手术日期、生存结局等）不许长期停留在 JSONB。**

### 6A.5 值域扩展

枚举值的增减比字段更频繁（如手术方式新增一种术式）：

- 值域独立存 `value_domain_registry`，与字段解耦。
- 新增枚举值只需在值域表加一行，**不需要 migration、不需要发版**。
- 但**枚举值只能新增、不能删除**——历史数据可能已经用了它。要停用则标 `deprecated`，新录入不再可选、历史数据仍可解析。

---

### 6A.6 登记节奏：首批一次性 + 后续逐步增加【医疗团队 2026-08-12 确认】

字段登记不要求一次登完，采用**首批集中 + 增量补充**：

| 阶段 | 登记范围 | 时点 |
|---|---|---|
| **首批** | 核心表全部字段（dim_patient、fact_clinical_event、fact_tumor_pathology、fact_treatment_outcomes、fact_followup_event） | S1，一次性完成 |
| **增量** | 随 Sprint 推进逐步补充：分子、用药、疗效、AE、并发症、转移灶、功能评价等 | S2-S4 |
| **持续** | 临床提出的新字段需求，随时走 6A.3 流程登记 | 长期 |

**关键要求**：增量登记走的是**同一套流程和同一张表**，不另开通道。首批之后新增字段属于日常运维动作，不是"二期改造"——这正是 field_registry 存在的意义：让加字段变成一件常规、低成本、有记录的事。

### 6A.7 谁来操作：三层权限模型

> 医疗团队提问：以后扩表、扩字段，是医生在管理后台操作吗？
> **答：分三层。医生能自助做一大部分，但物理表结构变更必须工程执行。**

#### 先排除一个错误方案：EAV 动态字段

有些系统为让用户"随时加字段"，采用 EAV 模式（字段名与值都存成数据行），点几下即可加字段、无需 migration。**本项目明确不采用**，代价不可接受：

| 代价 | 说明 |
|---|---|
| 查询性能崩塌 | 取一个患者 20 个字段需 20 次自连接 |
| 类型校验失效 | 所有值以文本存储，日期、数值无法约束 |
| 索引无法建立 | 高频筛选字段（分期、MSI）无法走索引 |
| 统计分析困难 | Table 1、KM、Cox 需要宽表，EAV 需大量透视转换 |

**结论**：物理列 + 元数据注册表的方案，牺牲一点"即时性"，换来性能、类型安全与可分析性。这个取舍对临床科研库是必要的。

#### 三层操作模型

| 层级 | 变更类型 | 谁操作 | 是否需 migration | 生效时间 |
|---|---|---|---|---|
| **L1 医生自助** | 值域枚举增补、字段中文名/定义/同义词/AI提示修改、显示分组与顺序调整、必填与否切换 | **医疗团队在后台直接操作** | 否 | **即时** |
| **L2 医生发起 + 工程执行** | 已有表新增字段、字段类型或值域绑定变更、字段停用 | 医生在后台填登记表 → 工程审核并生成 migration | 是 | 下个发布窗口 |
| **L3 医工联合设计** | 新建实体/事实表、实体关系调整、主键或关联键变更 | 医工共同评审后由工程实施 | 是 | 按 Sprint 排期 |

#### L1 详解：医生真正能自助的部分

这一层不碰物理结构，只改元数据，因此可以放开给医疗团队：

- **新增枚举值**：如手术方式新增一种术式、并发症类型新增一项。在 `value_domain_registry` 加一行即可，前端下拉框立即出现该选项。
- **完善字段说明**：中文名、医学定义、同义词、AI 提示。**这一项对 AI 抽取准确率影响最大**——发现 AI 老抽错某个字段，医生自己补同义词即可改善，不必找工程。
- **调整表单布局**：字段分组、显示顺序、是否必填。直接影响治理工作台的录入效率。

**约束**：枚举值**只能新增、不能删除**（历史数据可能已使用），停用则标 `deprecated`——新录入不再可选，历史数据仍可解析。

#### L2 详解：新增字段的完整流程

```
医生在后台「字段申请」页填写：
  ├─ 中文名、医学定义
  ├─ 归属哪张表（系统按 5.6 给出建议）
  ├─ 数据类型、值域、单位
  ├─ 是否必填、是否参与完整度评分
  ├─ 权威源（system / expert）
  └─ AI 提示
  ↓ 提交（status = draft）
工程审核：
  ├─ 判断是否真需新列（可能已有同义字段、或应为派生标签）
  ├─ 评估对现有查询与索引的影响
  └─ 生成 Alembic migration
  ↓
dev 测试 → staging 验证 → 备份后 production
  ↓ status = active
前端表单自动出现该字段（schema-driven，无需前端发版）
AI 抽取自动纳入该字段
数据字典自动更新
```

**工程审核环节不可省**，它拦截三类常见问题：
1. **重复字段**——医生想加的内容已有字段承载，只是名字不同。
2. **本该是派生标签**——如"是否高危"，应进规则引擎而非物理列。
3. **归属错误**——如把随时间变化的指标（ECOG、体重）放进患者维度表，而非事件表。

#### 等不及发布窗口怎么办：JSONB 缓冲

医生临时需要记录某项内容、但字段尚未上线时，走 6A.4 的第三种扩展：**先落 `event_store` JSONB 保住数据**，不阻塞临床工作；待字段正式上线后，由 ETL 将 JSONB 中的历史值回填至新列。

**这是缓冲机制，不是长期方案**——核心字段（TNM、MSI、KRAS、手术日期、生存结局）不得长期停留在 JSONB。

#### 变更频率与设计匹配

| 变更类型 | 预期频率 | 对应层级 | 设计取向 |
|---|---|---|---|
| 枚举值增补 | 高（每月可能数次） | L1 | 完全自助、即时生效 |
| 字段新增 | 中（每季度若干） | L2 | 有审核、随发布窗口 |
| 新建实体表 | 低（半年至一年若干） | L3 | 联合评审、慎重 |

**设计原则**：**频率越高越自助，风险越高越审慎。** 这样既不让医生被工程排期卡住，也不让库结构失控。

#### 全程留痕

三层操作均写入 `audit_log`：谁在何时改了什么、原值与新值、变更理由、审批人。字段与值域的变更历史必须可回溯——将来发现某批数据异常时，需要能查到"这个字段是什么时候加的、值域什么时候改过"。

## 6B. AI 辅助字段识别与录入

> 需求：医生录入信息时，通过 AI 识别匹配字段内容。
> 定位：**AI 只做候选，不做决定。** 这是硬边界，见第 11 章。

### 6B.1 应用场景与工作方式

典型场景：医生粘贴一段手术记录或病理报告文本，系统自动识别出其中的结构化信息，填入对应字段供医生确认。

```
医生粘贴自由文本（手术记录 / 病理报告 / 出院小结）
  ↓
后端调用本地模型（内网 Ollama，明文数据不出内网）
  ↓
读取 field_registry：字段中文名 + 定义 + 同义词 + 值域 + ai_hint
  ↓
模型输出候选：{字段, 抽取值, 原文片段, 置信度}
  ↓
值域校验（枚举字段必须落在合法值域内，否则降级为"待确认"）
  ↓
前端高亮展示：字段旁显示 AI 建议值 + 原文出处
  ↓
医生逐项确认 / 修改 / 拒绝
  ↓
确认后入库，标记 extracted_by_ai + review_status=confirmed + reviewed_by
```

### 6B.2 为什么必须读 field_registry 而不是硬编码提示词

如果把字段说明写死在提示词里，每次加字段都要改代码、且 AI 与数据库容易不同步。读注册表则：

- 新字段注册后 AI **自动知道**它的存在、含义、值域。
- 同义词表让 AI 认得临床习惯写法（"吻合口瘘"和"吻合口漏"是同一个字段）。
- `ai_extractable=false` 的字段（如需要专业判断的分级、派生字段）**自动被排除**，AI 不会去猜。

### 6B.3 硬边界

| 允许 AI 做 | 禁止 AI 做 |
|---|---|
| 从文本抽取候选值 | 直接写入数据库（必须经医生确认） |
| 给出字段匹配建议 | 判定患者身份合并 |
| 标注原文出处 | 决定 CD 分级、TNM 分期等专业判断（可给候选，但必须医生确认） |
| 给出置信度 | 填充 `is_derived=true` 的派生字段（这些必须走规则引擎） |

**特别注意**：`authority_source=expert` 的字段（手术细节、临床评估、并发症分级）即使 AI 抽出候选，也必须医生确认才能入库——这与 12.1 仲裁原则一致。

### 6B.4 审计要求

AI 参与的每条数据必须记录：`extracted_by_ai=true`、`ai_model_name`、`ai_prompt_version`、`source_text_snippet`（原文片段，供回溯）、`ai_confidence`、`review_status`、`reviewed_by`、`reviewed_at`。

**保留原文片段是关键**：将来发现某个字段抽错了，能定位到是哪段文字被误解，从而改进提示词或同义词表。

### 6B.5 本轮实现范围建议

AI 抽取不必一次做全。建议本轮只做**两类低风险高收益字段**：

1. **明确枚举型**：手术方式、手术入路、造口类型——有值域约束，AI 出错也会被值域校验拦住。
2. **明确数值/日期型**：手术日期、住院天数、出血量——格式规整，易验证。

**暂不做**：TNM 分期、CD 分级、疗效评价等需要专业判断的字段。这些等前两类跑稳、准确率有实测数据后再评估。

### 6B.6 部署方案选型：本地 / 云端 / 混合【医疗团队 2026-08-12 提出云端诉求，此处给出判断】

#### 前置澄清：加密不能解决云端隐私问题

医疗团队提出"把 AI 抽取放云端，重点做数据加密"。此处必须先厘清一个技术事实：

> **云端大模型无法在密文上做推理。** 文本必须在云厂商服务器上**解密为明文**才能被模型读取——这是 Transformer 推理机制决定的，非厂商意愿问题。

因此：
- 通常所说的"加密"指**传输加密（TLS）**，防的是链路第三方窃听，**防不了云厂商本身**；数据到对端即为明文。
- **同态加密**理论上可在密文上计算，但用于 LLM 推理的性能开销是数个数量级，工程上不可用。
- 结论：**把病历原文发往公网大模型，等同于把明文病历交给一家外部公司**，加密与否不改变这一事实，且直接违反启动细则"明文患者数据不得进入公网 AI"。

#### 真正使云端可用的机制：本地去标识化

若要使用云端能力，正确路径不是加密，而是**发出前就让它不再是患者数据**。关键约束：**去标识化必须在本地完成**——若指望云端代做，数据已经出去了，失去意义。

#### 三种方案对比

| 方案 | 数据流 | 隐私风险 | 合规门槛 | 成本 | 顾问评估 |
|---|---|---|---|---|---|
| **A 纯本地** | 明文不出内网 | 最低 | 无需外部审批 | 一次性硬件 1.5-5 万 | ✅ **推荐** |
| **B 混合（本地去标识 + 云端抽取）** | 本地脱敏 → 云端明文（已脱敏）→ 本地回填 | 中，存残余再识别风险 | **须信息中心 + 伦理 + 法务批准** | 硬件（小模型）+ API 调用费 | ⚠️ 可行但需过关卡 |
| **C 纯云端** | 病历原文出网 | 高 | **违反启动细则红线** | 仅 API 费 | ❌ 不建议 |

**方案 B 的残余风险（必须如实告知审批部门）**：临床自由文本的去标识化**无法做到 100%**。罕见病情组合、特殊术式、医生姓名、转诊机构名等均可能构成再识别线索。是否接受该残余风险，由医院信息中心与伦理委员会判定，工程侧不能自行决定。

#### 关于"本地模型能力不足"的评估

该顾虑通常来自通用对话场景的体验，但本项目的任务性质不同——**这是受约束的抽取任务，不是开放推理**。三个约束大幅降低难度：

1. **值域兜底**：手术方式等枚举字段只能从代码表候选中选，模型在做选择题而非自由生成。
2. **领域极窄**：仅结直肠癌手术、病理、随访几类文本，非通用知识。
3. **人工必审**：每条候选均需医生确认，本就不依赖模型百分百准确。

在此约束下，Qwen2.5-14B/32B 量级开源模型做中文临床文本结构化抽取，能力已足够。**决定效果的主要变量是 `field_registry` 中字段定义与同义词的质量，而非模型参数量**——这正是把注册表设计为 AI 知识来源的原因。

### 6B.7 本地部署硬件规格

| 档位 | 硬件 | 可运行模型 | 参考成本 | 说明 |
|---|---|---|---|---|
| 入门 | RTX 4090 24G ×1 | 14B / 32B（4bit 量化） | 1.5–2 万 | 单次抽取 3–5 秒，满足交互 + 夜间批处理 |
| **推荐** | RTX A6000 / L40S 48G | 32B 并发舒适 | 3–5 万 | 多人同时使用不排队 |
| 高配 | A100 80G 或 4090 ×2 | 70B 级 | 8 万+ | 边际收益有限 |
| 替代 | Mac Studio M2/M3 Ultra 192G | 70B（统一内存） | 4–6 万 | 速度较慢但部署简单；启动细则已提及该节点形态 |

**吞吐估算**：1.7 万患者 × 每人 2–3 份文书 ≈ 5 万次抽取；4090 上 14B 模型按 5 秒/次计，约 70 小时 = **三个夜间批处理完成**。存量为一次性成本，后续增量压力远小于此。

**结论**：单张 4090 即可起步。该投入显著低于将病历外发所需承担的合规成本与风险。

### 6B.8 采用路线：方案 B 混合架构【医疗团队 2026-08-12 决定】

医疗团队确认：**采用去标识化路线，患者基础信息不上云即可。**

**落地口径**：
- 本地完成去标识化 → 脱敏文本送云端抽取 → 结构化候选返回本地 → 本地回填并经医生确认。
- **绝不出网的内容**：姓名、身份证、住院号、联系方式、住址、患者主索引、机构名、医生姓名。
- **可出网的内容**：去标识后的临床描述文本（术式、病理、检验数值等）。

**必须完成的前置**：
1. 信息中心 + 伦理委员会 + 法务三方审批，明确接受去标识化残余风险。
2. 与云厂商签署数据处理协议，明确不留存、不用于训练。
3. 去标识化模块须先通过**抽样人工验证**（建议 200 份以上，确认无身份信息泄漏）方可开闸。

**架构要求**：`ai/extractor` 推理后端可插拔（本地 / 云端配置切换），保留本地兜底能力——审批未通过或云端不可用时，可退回本地模型运行，不阻塞业务。

## 6C. 大规模字段的 AI 抽取工程设计

> 医疗团队提出：几十张表、几百个字段的规模下，云端 AI 抽取怎么做。
> 这是本方案 AI 部分最关键的工程问题——**不解决它，AI 抽取在真实规模下不可用。**

### 6C.1 为什么不能把所有字段一次性交给模型

假设 500 个字段，每个字段的名称、定义、值域、同义词平均 80 token，光字段说明就 4 万 token。这会同时引发三个问题：

| 问题 | 后果 |
|---|---|
| 上下文膨胀 | 超出窗口或成本极高；即便塞得下，单次调用费用与延迟不可接受 |
| **注意力稀释** | 这是最致命的——字段越多，模型对每个字段的关注度越低，准确率显著下降 |
| 语义干扰 | 相似字段（如"术前 CEA"与"术后 CEA"、"初诊分期"与"术后分期"）互相混淆，误填率上升 |

**核心结论**：**一份文书只涉及全库字段的一小部分**。一份手术记录不会包含随访信息、不会包含分子检测结果。所以正确做法不是"把所有字段给模型"，而是**只给这份文书可能涉及的那几十个字段**。

### 6C.2 解法总览：三级收敛

```
一份文书（如手术记录）
  ↓ ① 文书类型识别 —— 判断这是什么文书
  ↓ ② 字段域路由 —— 按类型取出候选字段集（500 → 30~50）
  ↓ ③ 分组切分 —— 字段仍多时按语义分组，多次调用（30~50 → 每组 10~15）
  ↓ 抽取 → 合并 → 值域校验 → 医生确认
```

三级收敛后，**单次调用只面对 10-15 个字段**，注意力集中、准确率高、成本可控。

### 6C.3 第一级：文书类型识别

先判断"这是什么文书"，这一步很轻，可用规则 + 小模型完成：

| 文书类型 | 识别特征 | 对应字段域 |
|---|---|---|
| 手术记录 | "麻醉方式""切口""吻合""术中出血" | 手术域 |
| 病理报告 | "肉眼所见""镜下""免疫组化""pTNM" | 病理域 + 分子域 |
| 出院小结 | "入院诊断""诊疗经过""出院医嘱" | 住院域 + 诊断域 |
| 影像报告 | "MRI""CT""所见""印象" | 影像评估域 |
| 随访记录 | "随访""复查""末次" | 随访域 + 复发转移域 |
| 化疗记录 | "方案""周期""剂量" | 用药域 + 不良事件域 |

一份文书可命中多个域（如病理报告同时涉及病理域与分子域），取并集。

### 6C.4 第二级：字段域路由（field_registry 扩展）

在 `field_registry` 增加两个字段支撑路由：

| 新增字段 | 说明 |
|---|---|
| `field_domain` | 字段所属语义域：surgery / pathology / molecular / medication / followup / adverse_event / imaging / admission |
| `applicable_doc_types` | JSONB，该字段可能出现在哪些文书类型中 |

路由逻辑：文书类型 → 查 `applicable_doc_types` → 得到候选字段集。**500 个字段收敛到 30-50 个。**

这是纯查表操作，不消耗模型能力，且随字段注册自动生效——新字段登记时填好 `applicable_doc_types`，路由自动纳入，无需改代码。

### 6C.5 第三级：语义分组切分

若候选字段仍超过 15 个，按 `field_domain` + `ui_group` 再切分，分多次调用。以手术记录为例：

| 分组 | 字段示例 | 一次调用 |
|---|---|---|
| 手术基本信息 | 手术日期、术者、麻醉方式、手术时长 | 第 1 次 |
| 术式与入路 | 手术方式、入路、平台（腹腔镜/机器人/开放） | 第 2 次 |
| 吻合与造口 | 吻合方式、吻合口距肛缘、造口类型、造口原因 | 第 3 次 |
| 术中情况 | 出血量、输血、中转开腹、术中并发症 | 第 4 次 |

**每次调用只带 10-15 个字段的完整说明**，注意力集中。各次结果按字段名合并，互不干扰。

### 6C.6 长文本的切分策略

文书本身过长时（如完整出院小结），按**章节切分而非按字数硬切**：

- 优先按文书自带小标题切（"入院诊断""诊疗经过""出院情况"）。
- 每段只送给与之相关的字段组——"诊疗经过"段不必去问病理字段。
- 硬切时保留 10-15% 重叠，避免关键句被切断。

### 6C.7 兜底：语义检索路由

上述路由靠 `applicable_doc_types` 的人工标注。若遇到未预料的文书类型、或标注不全，用兜底机制：

1. 把 `field_registry` 中所有字段的「中文名 + 定义 + 同义词」预先向量化，存入向量索引（本地，不出网）。
2. 文书分段后计算段落向量，检索 Top-K 相似字段作为候选。
3. 与规则路由结果取并集，避免漏字段。

**注意**：向量化在本地完成，索引里只有字段说明、不含患者数据，无隐私风险。

### 6C.8 成本与吞吐估算（云端方案）

以 1.7 万患者、每人 3 份文书、每份平均触发 4 次分组调用计：

| 项 | 估算 |
|---|---|
| 总调用次数 | 1.7万 × 3 × 4 ≈ **20 万次** |
| 单次输入 | 脱敏文本片段 ~800 token + 字段说明 ~1200 token ≈ 2000 token |
| 单次输出 | ~200 token |
| 总 token | 输入 4 亿 + 输出 0.4 亿 |

**成本控制手段**（必须实现，否则费用不可控）：

1. **缓存字段说明**：同一字段组的说明在多次调用中重复，用 prompt caching 可大幅降低重复输入成本。
2. **先过规则再调模型**：结构规整的内容（日期、数值、明确关键词）先用正则抽，抽到就不调模型。经验上可拦掉 30-50% 的调用。
3. **增量处理**：存量一次性跑完后，日常只处理新增文书，量级骤降。
4. **分级路由**：简单字段用便宜模型，复杂字段才用高级模型。

### 6C.9 一致性与质量控制

大规模抽取必须有质量闸门，否则错误会批量入库：

| 机制 | 说明 |
|---|---|
| 值域强校验 | 枚举字段抽取值必须落在 `value_domain_registry` 内，否则降级"待确认"、不进候选 |
| 交叉校验 | 同一字段被多份文书抽出不同值时（如手术日期），标记冲突、交人工判定，不自动取其一 |
| 置信度阈值 | 低于阈值的候选不展示为建议，只标"疑似"，避免误导医生 |
| 抽样审计 | 每批抽取后随机抽 5% 人工复核，统计各字段准确率，写入监控 |
| 逐字段准确率看板 | 按字段统计 AI 建议被医生接受/修改/拒绝的比例，准确率低的字段回头改 `ai_hint` 与 `synonyms` |

**最后一条最重要**：它让系统能自我改进——哪个字段抽得差，就去补它的定义和同义词，而不是笼统地说"AI 不准"。

### 6C.10 实施顺序建议

不要一上来做全部字段，按域分批上线：

| 批次 | 范围 | 目的 |
|---|---|---|
| 第 1 批 | 手术域（枚举 + 数值日期型） | 验证链路，字段少、值域明确、易验收 |
| 第 2 批 | 病理域 | 文本结构化程度高，收益大 |
| 第 3 批 | 用药域、随访域 | 表述较自由，需更多同义词打磨 |
| 暂缓 | 需专业判断的字段（TNM、CD 分级、疗效评价） | 等前三批准确率数据出来再评估 |

每批上线后跑一轮抽样审计，准确率达标再进下一批。

### 6C.11 关键澄清：文书分类 ≠ 表分类（工程实施必读）

> 医疗团队提问：导入文档要先分类（手术记录/检查报告），那建表时是不是也按这个分类？
> **答：不是。这是两套不同的分类轴，且不能对齐。混淆二者会导致表结构设计错误。**

#### 两者的性质完全不同

| | 文书分类 | 表分类 |
|---|---|---|
| 分类依据 | 医院**用什么格式**写的（手术记录/病理报告/出院小结…） | **医学上这是个什么东西**（病理事实/并发症事件/转移事件…） |
| 存在时机 | **仅存在于接入加工环节**，抽取完即失效 | **长期存在**，是库的骨架 |
| 作用 | 决定这份文书该问哪几十个字段（字段路由） | 决定事实存在哪里 |
| 是否落库为结构 | **否**（仅作为 `source_doc_type` 血缘属性记录） | 是 |

**一句话**：文书类型是流水线上的一道工序，不是仓库的货架。

#### 二者是多对多关系

一份文书往往喂多张表，一张表也往往由多种文书喂：

| 一份文书 → 多张表 | 一张表 ← 多种文书 |
|---|---|
| **病理报告** → `fact_tumor_pathology`（组织学类型、分化、pTNM、脉管侵犯）+ `fact_molecular`（若含免疫组化 MMR） | **`fact_complication`** ← 手术记录（术中并发症）+ 出院小结（术后并发症）+ 随访记录（晚期并发症） |
| **手术记录** → `fact_clinical_event`（手术事件）+ `fact_treatment_outcomes`（术式/入路/吻合）+ `fact_complication`（术中并发症） | **`fact_metastasis`** ← 影像报告 + 病理报告 + 随访记录 |

#### 为什么绝不能按文书类型建表

| 后果 | 说明 |
|---|---|
| **换数据源即失效** | 他院手术记录格式与字段不同，表就对不上。本项目从第一天即多中心，此问题必然发生 |
| **同一事实被劈散** | 并发症散落在"手术记录表/出院小结表/随访表"三处，统计"该患者全部并发症"需跨表拼接且口径难对齐 |
| **违反启动细则原则 1** | "表结构必须围绕医学实体、事件和关系设计，而不是简单复刻 Excel 表头"——按文书建表正是此禁令所指 |

#### 二者如何连接：靠 field_registry 转换

不需要让两套分类对齐，中间由字段注册表做转换：

```
文书进来
  ↓ 识别文书类型（如"手术记录"）
  ↓ 查 field_registry.applicable_doc_types → 得到候选字段集
  ↓ AI 抽取各字段的值
  ↓ 每个字段按 field_registry.table_name 各回各的表
      ├→ fact_clinical_event
      ├→ fact_treatment_outcomes
      └→ fact_complication
```

**文书类型只在路由时使用一次**，随后作为 `source_doc_type` 记入血缘（用于追溯"这个值是从哪份文书抽出来的"），不参与表结构设计。

#### 工程红线

**禁止创建以文书类型命名的事实表**，如 `fact_surgery_record`、`fact_pathology_report`、`fact_discharge_summary`。
事实表必须以**医学实体或事件**命名。staging 层可按文书类型分区暂存原始内容，但**不得延续到星型层**。

## 7. 接入层与主数据管理

### 7.1 身份链接策略（高风险模块）

**核心原则：宁可漏合并，不可错合并。** 错合并会把两个患者的病理、治疗、随访、生存结局混为一条，且不报错、难发现，污染的正好是 OS/DFS/分期这类核心字段。

| 判定类型 | 依据 | 处理 |
|---|---|---|
| **自动合并** | 身份证号完全一致 / 院内唯一号完全一致且来源可信 / 合法哈希身份键完全一致 | 系统自动链接 |
| **进人工复核队列** | 姓名+年龄+日期相似 / 姓名+性别+院区相似 / 同名不同证件 / 同证件不同姓名 / 同名不同年龄 | 生成候选，**不落 patient_id** |
| **禁止合并** | 仅姓名相同 / 仅手机号相同且无其他证据 / 仅年龄相近 / 模糊算法得分高但无确定性标识 | 拒绝，记录原因 |

**工程实现要点**：
- `identity_linkage_map` 存候选，字段含 `match_type` `match_score` `evidence` `review_status` `reviewed_by`。
- 模糊匹配得分再高也只写候选表，**代码中不得存在"得分超过阈值即自动合并"的分支**。
- 复核队列由医疗团队处理，工程侧只提供界面与审计。
- 合并操作必须可逆：保留合并前的原始记录关系。

### 7.2 质量闸门

不合格数据不进真相源，进隔离区等治理：

| 闸门级别 | 判定 | 处理 |
|---|---|---|
| 硬阻断 | 缺 patient 标识、日期非法、TNM 不符枚举 | 拒绝入库，进 `dq_exception_log` |
| 软告警 | 关键字段缺失、极值可疑 | 入库但标记，生成治理任务 |
| 通过 | 全部规则通过 | 正常入库 |

### 7.3 清洗规则注册化

规则从硬编码迁移到 `dq_rule_registry` + `value_domain_registry`，示例：

- 性别枚举：男 / 女 / 未登记
- OS_days ≥ 0
- 生存状态=死亡时 death_date 不得为空
- 身高单位米/厘米自动识别
- 体重、BMI、费用、住院天数剔除极值
- CEA、CA19-9 不允许负值
- TNM 分期符合标准枚举

**要求**：规则可配置、可版本化、可单独启停，不得写死在 ETL 脚本里。

## 9. 接口规范

### 9.1 通用要求

所有 API 必须：结构化 JSON、统一错误格式、分页、参数校验、日志、权限控制、审计留痕、不暴露数据库异常栈。

1. 当前用户角色是否允许治理
2. 字段是否在治理白名单内

每次修正记录：`patient_id` `event_id` `table_name` `field_name` `old_value` `new_value` `updated_by` `updated_at` `updated_ip` `reason` `source_evidence` `review_status`。

## 10. 安全与合规实现

### 10.1 脱敏四级

| 等级 | 实现 | 可访问角色 |
|---|---|---|
| raw | 明文 | 核心治理人员，内网 |
| masked | 姓名/电话/证件部分掩码 | 普通院内查看 |
| pseudonymized | patient_id 假名化 | 科研分析 |
| anonymized | 去除可识别身份，不可回溯 | 外部统计展示 |

### 10.2 硬性边界

**禁止**：明文患者数据进公网 AI、进未授权云服务、前端导出明文身份证/电话/住址、经个人网盘或非受控聊天工具传输。

**允许**：内网服务器处理明文、内网部署本地模型、脱敏样例调试、schema 与字段字典用于 AI 辅助开发。

### 10.3 基础安全项

JWT 登录、短会话有效期、RBAC、强密码哈希、操作审计、IP 记录、导出审计、明文字段访问控制、备份加密、最小权限。

### 10.4 合规参考

HL7 FHIR（互操作）、OMOP CDM（多中心 RWD 兼容）、ISO/IEC 27001（安全管理）、个人信息保护法。**均为设计参考，是否构成合规结论由医院信息中心、伦理、法务确认。**

## 12. 医学口径补充说明（必须进数据字典）

> 以下四项是历轮医学讨论已拍板、但启动细则未覆盖的内容。工程实现时必须按此配置，不得自行简化。

### 12.1 数据仲裁原则（按数据性质分流）

冲突时不是一律信谁，而是**按字段类别路由到对应权威源**：

| 数据性质 | 权威源 | 举例 |
|---|---|---|
| 客观计费、系统精确计量 | **HIS / 医保系统** | 药品、耗材品牌型号数量、费用、DRG 分组 |
| 临床判断、专业评估 | **临床专家** | 手术细节、保肛决策、并发症分级、疗效评价 |

**工程实现**：
- 每个字段在数据字典中标注 `authority_source`（system / expert）。
- 冲突时按标注取值，**另一来源的值不删除**，降级留档并写冲突记录（冲突项、两来源值、以谁为准、判定人、时间）。
- 字段带 `value_source` 标记最终值来自哪里，供质控回看与反哺规则。

理由：HIS 提取的计费类数据比医生回忆准确；但手术细节与临床评估必须由专家判定。

### 12.2 主观数据准入线

**不可核验、不可复现的主观数据不进基座。**

- 患者满意度类数据依赖额外问卷采集，无法从 HIS 或医保系统客观获得，**本轮不纳入**。
- 若将来纳入，必须先明确采集方式、量表版本、可复现性，再进基座。
- 工程侧不为此预建字段，避免建了长期空置。

注意：这条与"患者体验"作为评价维度不矛盾——患者体验维度中**可客观测量**的部分（LARS 条目得分、造口状态、并发症）照常入库，只有主观满意度打分被挡在准入线外。

### 12.3 转移时序判定口径（已拍板）

| 项 | 定稿值 |
|---|---|
| 基准日锚点 | **原发灶手术日**；未手术病例退回诊断日 |
| 阈值 | **≥6 个月**为异时性，<6 个月为同时性 |
| 参数化 | 锚点与阈值均为规则参数、带版本，改口径重算即可 |
| 特例 | 初诊即 M1 者单独打标，**不参与"术后新发"推导** |

**必须存的原子事实**：原发灶手术日、原发灶诊断日、初诊 M 分期及是否影像确认、转移灶多条记录（首检日 / 部位 / 检出方式）。

**工程注意**：不得把"间隔≥6月=异时性"写死为物理列。这是阈值不是定义——术后 8 个月查出的肝转移也可能是初诊时就存在的隐匿病灶。标签必须可推导、可复核、可重判。

### 12.4 cCR ≠ pCR（口径混用风险）

| 概念 | 全称 | 判定依据 | 适用人群 |
|---|---|---|---|
| **pCR** | 病理完全缓解 | **术后标本**病理，本质等于 TRG=0 | 已手术者 |
| **cCR** | 临床完全缓解 | 影像 / 内镜评估 | 含 watch & wait 非手术者 |

**风险**：watch & wait 人群只有 cCR、没有 pCR（无手术标本）。若两者混用，会把非手术患者错误计入 pCR 分母或分子。

**工程要求**：两者必须是**两个独立字段**，数据字典中显式标注判定依据与适用人群，禁止合并为一个"完全缓解"字段。

### 12.5 其他已定稿口径

| 项 | 口径 |
|---|---|
| 并发症记录 | 一患者可多条，每条含：类型（挂标准术语）、CD 级别、是否有干预、干预措施（可多项）、干预效果 |
| CD 分级本质 | 按**矫正所需干预强度**客观分级，依据"做了什么"而非"叫什么"，故应可推导而非主观录入 |
| 录入策略 | 分层：①自动获取（HIS/上传 + 可推导的自动算）②医生主动填（保留入口）③仅推不出的标"待补充"，只补缺的那一格 |
| LARS | **独立功能评价事件表**，一患者多条（按时点）；只存条目级原始得分为原子事实，总分与分级由规则推导 |
| LARS 双重身份 | 既可作参数被其他分析取用，也可作独立研究入口（以 LARS 为主结局立题）。故必须建成独立事件表 + 完整时序，不可压成患者身上的标量字段 |
| 耗材与用药 | **两张独立事实表**，评估点不同（耗材=经济性+创新性，用药=疗效+安全性），只共享住院/手术关联键 |

### 12.6 尚待医疗团队确认的口径（不阻塞开发，但需在对应 Sprint 前定）

1. 费用粒度：按 11 个医保分项建、总费用作派生？（顾问建议：是，细粒度可倒推粗粒度）
2. 30 天再入院：新建独立字段，还是复用随访事件打标？（顾问建议：复用随访事件，避免两处记录对不上）
3. LARS 量表版本：国际标准版（5 条目 / 0-42 / 三档）还是本院调整版？
4. LARS 评估时点：固定时点（3月/6月/1年/2年）还是跟门诊随访走？
